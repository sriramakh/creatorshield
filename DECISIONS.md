# Decisions

| # | Decision | Why | Trade-off |
|---|---|---|---|
| 1 | Run services **natively** (Homebrew Postgres/Redis, `scripts/dev.sh`); Docker Compose provided as an alternative | Docker Desktop on a 16 GB Mac costs several GB of RAM; all deps were already installed | Two setup paths to maintain |
| 2 | Postgres started with `pg_ctl`, not `brew services` | `brew services` crashed on the `postgresql@17` formula (Homebrew bug); `pg_ctl` also avoids auto-start at login | Must run `scripts/dev.sh` after a reboot |
| 3 | **faster-whisper `small`, int8, CPU** for speech-to-text | Free, local, ~3–7 s per 60 s clip on M4 after load; usable Hindi; ~480 MB model | Hindi ASR still makes spelling errors; `medium` is better but slower/larger |
| 4 | Decode audio ourselves and pass samples to faster-whisper | faster-whisper's internal decoder calls a PyAV API (`metadata_errors`) removed in the installed PyAV | Requires 16 kHz mono WAV (which we produce anyway) |
| 5 | Frame sampling = scene changes (FFmpeg `select=gt(scene,0.25)`) + uniform every 4 s, capped at 16, scene changes prioritised | Covers cuts and steady shots; bounded token cost | Short flashes between samples can be missed (documented limitation) |
| 6 | No OpenCV | FFmpeg scene detection covers MVP needs; avoids a heavy dependency | Less flexible vision preprocessing |
| 7 | Tesseract CLI OCR (eng / hin+eng), confidence ≥ 70 | Already installed, free, language packs present | Struggles with stylised fonts; Devanagari must be correctly shaped |
| 8 | Non-speech sound detection via `silencedetect` minus speech segments | Cheap, deterministic signal for "possible music → licensing uncertainty" | Cannot tell music from ambient noise; never identifies tracks |
| 9 | **RQ SimpleWorker** (no fork per job) | Avoids macOS Objective-C fork-safety crashes; keeps the Whisper model warm between jobs | One job at a time per worker process (run more workers to scale) |
| 10 | Deterministic checks always run, AI optional | Product still useful (and honest) without a key or when the AI call fails | Some overlap with AI findings → solved by merge (#13) |
| 11 | Provider-native structured outputs **plus** server-side validation | Schema compliance from the provider; semantic checks (citations, evidence IDs, timestamps) need our own code | Two layers to keep in sync with `AIAnalysisOutput` |
| 12 | Own rule IDs mapped 1:1 to official pages | Platforms don't publish rule numbers; stable IDs make citations checkable | IDs are ours, not the platform's — stated in UI |
| 13 | Merge rule findings into AI findings only on **same category** (shared evidence or overlapping time) or **strong** cross-category evidence overlap (≥2 refs and ≥⅔) | First live run showed a looser rule folding a disclosure finding into a health-claim finding via one shared transcript line | Occasionally two related findings stay separate |
| 14 | "Suspected" and "licensing" findings always require human review | They are judgements by definition; the model sometimes said no review needed | More items flagged for review |
| 15 | OpenAI default model `gpt-5` for live testing | Key had access to many newer models whose pricing I could not verify; gpt-5 pricing/capabilities known; user approved < $1 testing | Newer models (gpt-5.5, gpt-6-*) may give better results — evaluate before switching |
| 16 | Images sent to OpenAI at `detail: low` | Keeps input ≈ 5k tokens/video; OCR text is provided separately | Fine visual detail may be missed |
| 17 | Next.js 16 with Cache Components (scaffold default); data fetched client-side from FastAPI with CORS | Simple separation; avoids Next rewrite body-size limits for uploads | Pages stay mounted (Activity) after navigation — handled (video pause, form reset, scoped selectors) |
| 18 | HTML report (self-contained, printable) + JSON instead of server-side PDF | No extra system libraries; browser "Print → PDF" gives a PDF | No one-click PDF yet |
| 19 | Store schema-valid raw AI output (`analyses.ai_output`) | Audit trail; lets merge/validation changes be re-tested offline without paying for new API calls | Slightly more data retained (deleted with the analysis) |
| 20 | No authentication in v0.1 | Local single-user MVP scope | **Must** be added before any shared/public deployment |
| 21 | Links only via **connected accounts + official APIs**; no scraping / `yt-dlp` / anonymous URLs | YouTube API policies forbid scraping, downloading and separating audio/video; Meta prohibits automated collection; ownership becomes verifiable | Requires OAuth apps, user consent, platform review for production |
| 22 | YouTube imports are **metadata-only** | Policy forbids downloading AV content even for owners | Much weaker than video analysis; clearly labelled, upload offered |
| 23 | YouTube captions behind an opt-in scope (`youtube.force-ssl`) | Least privilege — that scope reads as "manage your YouTube account" | Without it, no transcript for YouTube imports |
| 24 | Instagram: use `media_url` when present, else caption + thumbnail | Official API provides the owner's Reel file, but omits it for licensed audio / copyright flags | Many trending-audio Reels get the limited review |
| 25 | Imported Reels > 60 s are trimmed to 60 s (uploads still rejected) | Reels are often 60–90 s; keeps cost/latency bounded | Later parts of long Reels are not analysed (stated in report) |
| 26 | OAuth tokens Fernet-encrypted; key in `.env`; state in Redis (single-use, 10 min); PKCE for Google | Standard protections against token theft and CSRF / code interception | Losing the key = reconnect accounts |
| 27 | Disconnect deletes all analyses imported via that connection; YouTube imports retained ≤ 30 days | YouTube API policy (delete within 7 days of revocation; refresh/delete within 30 days) | Imported history disappears on disconnect |
| 28 | Fake platform server (`tests/fake_platforms.py`) for tests + browser E2E | Exercise real OAuth/import code paths without credentials or network | Fake can drift from real APIs — live verification still required |
| 29 | Full review of a published post uses **the creator's own file**, cross-checked against official metadata. No platform AV download, no audio fingerprinting | YouTube forbids downloading AV; Instagram withholds many Reel files. The creator already has the original via their export tools. Fingerprinting needs a licensed reference database this product does not have | A file that is not the published cut can be reviewed by mistake — duration and caption-track mismatches are flagged, not silently trusted. Copyright clearance is still impossible here |
| 30 | Copyright review = **provenance leads + the creator's own rights ledger**, not a clearance | Content ID / Rights Manager reference data is not available to third parties; licences are private. What can be checked is where content may have come from and whether the creator has recorded a right to it | Findings say "no licence recorded", never "infringing"; the ledger is self-declared and not verified with counterparties |
| 31 | Own **catalogue fingerprinting** (dHash frames + Chromaprint audio, offset-aligned) instead of a vendor | Free, local, no media retained; catches reposts and the same footage under two agency clients — the case agencies can't see today. Supersedes the "no audio fingerprinting" part of #29 (it fingerprints against the creator's own catalogue only) | Only knows videos indexed in this workspace; crops and heavy overlays weaken matches |
| 32 | Edge-masked 17×16 dHash (256 comparisons, flat areas ignored) | The first 9×8 dHash matched three unrelated text-on-colour sample videos to each other | Larger fingerprints (≈ 130 chars per frame); low-detail frames are skipped |
| 33 | Fingerprints outlive the 72 h analysis retention (`CATALOGUE_RETENTION_DAYS`, YouTube ≤ 30 d); explicit deletes remove them | A catalogue that forgets after 3 days cannot catch reposts. Hashes cannot reconstruct the video | One more data category to explain in a privacy notice |
| 34 | Paid lookups (AudD song ID, Google Vision web detection) **off by default**, opt-in per env var, triggered only by signals (music detected / third-party cues) or on request, cached, under one monthly budget cap | User asked to minimise cost; no paid calls without authorisation | Estimates ignore vendor free tiers (err high); vendor pricing unverified until accounts exist |
| 35 | YouTube look-alike search is on demand with a user-editable query and a daily quota cap | search.list costs 100 of 10,000 default daily units and matches text only | Finds re-uploads with similar titles/thumbnails, not arbitrary reuse |
| 36 | Third-party visual cues added to the existing AI prompt instead of a new model call | Zero marginal cost | Model judgement, labelled as licensing uncertainty with frame evidence |
| 37 | Recorded brand agreement + brand mentioned + no disclosure → **high**, observed finding (absorbs the generic promo-language finding) | The ledger turns a guess ("promo language") into a known material connection | Depends on the agency recording agreements |
| 38 | Cross-check mismatch is a report-validity verdict (`file_matches_post`), not a finding | Review of this branch: a wrong file scored "Moderate" risk under "originality" | Shown as a banner + top limitation instead of in the findings list |
| 39 | AI/rule licensing findings with potential ledger support remain counted and require human review; provenance coverage remains available for specific matches | A shared name or frame does not prove every concern in a free-text finding is covered | Duplicate reconciliation remains heuristic; historical covered findings remain displayable |
| 40 | Default limits raised to 20 min / 4 GB (configurable); frame budget 4 per minute within 16–64; media timeouts scale with length; fingerprint matching works in blocks (video) and ~30 s chunks with offset voting (audio) | Shorts are now up to 3 min (YouTube help 15424877) and Reels are reported at up to 20 min; agencies review long cuts. Measured on a 20-min file: audio matching peaked at 1.9 GB and video at 1.2 GB before chunking | AI cost per video grows with frames (64 frames at 20 min). Uploads are a single request, not resumable |
| 41 | 30 min / 5 GB limits; server-side **working copy** (H.264, short side ≤ 1080, ≤ 30 fps, metadata stripped) for files above 1080p or 8 Mbps; original hashed then deleted; `size_bytes` widened to BIGINT | Analysis never uses more than 1080p, so later passes read a file ~5-15× smaller, it plays in every browser, and disk use under retention drops. Browser-side compression (ffmpeg.wasm) cannot handle multi-GB files reliably | One extra decode up front (≈5× real time with hardware decode on an M-series Mac; slower in Linux containers without it). Files over 5 GB must be compressed before upload |
